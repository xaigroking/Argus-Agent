## 1. 为什么不直接用现成方案

| 方案 | 为何不采用 |
|---|---|
| Wazuh / Auditbeat + OpenSearch | 能力更全，但为 1–5 台主机跑 manager + indexer + dashboard，监控系统比被监控系统重一个数量级；且它们做通用主机审计，没有"归因到某个 AI Agent"的概念 |
| 自建内核采集（eBPF） | auditd 由发行版维护、有 CVE 流程、二十年打磨。重造这一层是净损失 |

**切换到 Wazuh 的条件（任一满足即应迁移）：** 主机数 > 20；需要等保 / ISO 现成报表；需要多租户权限隔离。本项目的 auditd 规则集可原样迁移，不浪费。

### 差异化：做归因，不做检测

检测引擎已有成熟方案，空白的是**"这次行为是谁 / 哪个 Agent 发起的"**。

后续引入横向移动、网段探测等深层能力时，**做集成方而非重实现方**：消费 Suricata / Falco 的告警，补上 `auid` + 进程血缘，输出"X 用户会话里的 Claude Code 发起了这次扫描"。

## 2. 架构

```
┌─ 内核 audit 子系统 ──────────────────────┐
│  execve / 文件访问 / 登录 / setuid        │   ← 用户无法绕过
└──────────────┬───────────────────────────┘
               │ auditd（发行版维护，我们不碰）
               ▼
      /var/log/audit/audit.log
               │ tail（含轮转处理）
               ▼
┌──────────────────────────────────────────┐
│  argus parse    低权用户 argus            │  ← 处理敌意输入的安全边界
│  解析 → 血缘归因 → 写入                    │
└──────────────┬───────────────────────────┘
               ▼
        SQLite（派生缓存，WAL）
               │ 只读连接
               ▼
┌──────────────────────────────────────────┐
│  argus serve    低权用户 argus            │
│  仅绑 127.0.0.1，M0–M3 不对外监听          │
└──────────────────────────────────────────┘
```

### 2.1 单二进制、多权限域

一个静态二进制、多个子命令，以不同用户跑不同 systemd unit：

| 子命令 | 运行身份 | 职责 |
|---|---|---|
| `argus rules` | root（仅安装时） | 下发 / 校验 auditd 规则 |
| `argus parse` | `argus` | 读日志、解析、归因、入库 |
| `argus serve` | `argus` | 只读库、本地 HTTP |
| `argus query` | 授权用户 | CLI 查询 |

单一交付物（部署简单），多个权限域（解析器被打穿也拿不到 root）。

**读取权限：** `audit.log` 为 `0600 root`。方案为给 `argus` 用户授予只读 ACL，或用 auditd 的 `log_group` 配置。**M0 必须实测确认**（发行版间有差异）。

### 2.2 为什么用 tail 而不是 audisp 插件

audisp 插件可获得亚秒级延迟，但我们的进程会进入 auditd 的调度链——一旦阻塞或崩溃会影响内核审计本身。

**S0 选择解耦：tail 日志文件，延迟数秒，我们崩了不影响审计完整性。**

### 2.3 SQLite 是派生缓存，不是真相源

**真相源是 `audit.log`。** 这条决定直接消灭了数据库迁移这个最大的升级负担：schema 要改就删库，从保留期内的日志重建，不需要迁移脚本、不需要向后兼容旧 schema。

代价：只能重建保留期内的数据。对审计场景可接受。

## 3. 数据模型（v0.1 草案）

```sql
-- 原始事件
CREATE TABLE events (
  id      INTEGER PRIMARY KEY,
  ts      INTEGER NOT NULL,   -- unix 毫秒
  serial  INTEGER,            -- auditd 事件序列号
  type    TEXT NOT NULL,      -- EXECVE / PATH / USER_LOGIN / ...
  auid    INTEGER,            -- 登录原始用户，归因的锚点
  uid     INTEGER,
  ses     INTEGER,            -- 审计会话 ID
  pid     INTEGER,
  ppid    INTEGER,
  exe     TEXT,
  argv    TEXT,               -- JSON 数组
  cwd     TEXT,
  tty     TEXT,
  cgroup  TEXT,
  akey    TEXT,               -- 规则 -k 标记
  success INTEGER,
  path    TEXT                -- 文件类事件的目标
);

-- 进程血缘（M2 核心）
CREATE TABLE processes (
  pid        INTEGER NOT NULL,
  start_ts   INTEGER NOT NULL,
  end_ts     INTEGER,
  ppid       INTEGER,
  exe        TEXT,
  argv       TEXT,
  auid       INTEGER,
  ses        INTEGER,
  cgroup     TEXT,
  root_label TEXT,            -- 归因结果：claude-code / codex / shell / cron / unknown
  PRIMARY KEY (pid, start_ts) -- pid 会复用，必须带时间
);

-- 登录会话
CREATE TABLE sessions (
  ses       INTEGER PRIMARY KEY,
  auid      INTEGER,
  start_ts  INTEGER,
  end_ts    INTEGER,
  src_addr  TEXT,
  tty       TEXT,
  result    TEXT              -- success / fail
);
```

**M1 必须落全 `ppid`、`cgroup`、`ses`** —— 漏采事后补不回来，M2 的归因全靠它们。

## 4. 进程血缘归因（M2 核心，最大技术难点）

目标：对任一条 execve，判断它是否出自某个 AI Agent。

### 4.1 难点与对策

| 问题 | 后果 | 对策 |
|---|---|---|
| 父进程退出后子进程被 init 收养 | **ppid 链断裂**，事后查不到真实祖先 | **按事件顺序增量维护** `pid → 祖先` 映射，不做事后查询 |
| pid 会复用 | 仅凭 pid 关联会张冠李戴 | 进程表以 `(pid, start_ts)` 为主键 |
| 单一锚点不可靠 | 归因错误 | **cgroup 路径作第二锚点**（Agent 通常在自己的 systemd scope 中，比 ppid 抗断链），两者交叉验证；不一致时标记 `unknown` 而非猜测 |

### 4.2 Agent 识别规则（配置驱动）

```toml
[[agents]]
name       = "claude-code"
match_exe  = ["claude"]
match_argv = []              # 可选：参数特征

[[agents]]
name       = "codex"
match_exe  = ["codex"]
```

放配置而非硬编码——Agent 工具迭代快，用户也可能自定义。

## 5. 技术选型

| 项 | 选择 | 理由 |
|---|---|---|
| 语言 | **Go** | 单静态二进制，目标机零运行时依赖，部署即拷贝 |
| 存储 | **SQLite（WAL）** | 零运维，单文件，便于按日期清理 |
| 采集 | **tail audit.log** | 与 auditd 解耦（见 §2.2） |
| 看板 | 内嵌静态页 + 标准库 HTTP | 不引前端构建链 |
| 解析 | 自写 | auditd 原始格式难啃但是已知量；引 Laurel 会多一个 Rust 依赖 |

## 6. 安全设计

### 6.1 核心认知：解析器处理敌意输入

被监控用户能控制进入 `audit.log` 的内容。用户执行 `echo '<script>alert(1)</script>'`，这串字符会流经解析器、数据库，最终渲染到看板——**存储型 XSS，攻击者就是被监控对象。**

同类风险：超长 argv 耗尽内存、异常字节让解析器错位、文件名中的引号拼进 SQL。

### 6.2 强制约束（可机器验证）

| 约束 | 防护目标 |
|---|---|
| 解析 / 展示均不以 root 运行 | 被打穿也拿不到 root |
| 看板默认仅绑 `127.0.0.1`，M0–M3 不开对外端口 | 外部攻击面为零 |
| 展示层使用只读数据库连接 | 打穿了也改不了审计数据 |
| **所有 SQL 参数化**，禁止字符串拼接 | SQL 注入 |
| **所有审计字段输出前强制转义** | 存储型 XSS |
| **解析器必须有 fuzz 测试**（Go 原生） | agent 最易写错的边界解析 bug |
| **禁止执行任何来自审计数据的内容** | 命令注入整类消除 |
| 单条事件与单字段设长度上限，超限截断并标记 | 资源耗尽 |

### 6.3 可信计算基要小

auditd 有发行版维护和 CVE 流程，我们的代码全部是它输出的**只读消费者**。新项目没有"上千双眼睛"的优势，唯一对策是让自己负责的代码少到一个人能看明白。

### 6.4 持续迭代的前提

**真实日志测试语料库（脱敏）是本项目能被持续修改的基础**：有机器可判定的回归测试，后续任何人或 Agent 改解析器才不是赌博。M1 建立，此后每个 PR 不得降低解析覆盖率。

## 7. 阶段范围

| 阶段 | 范围 |
|---|---|
| **S0**（当前） | 主机本地行为：进程执行、文件访问、登录会话、提权、Agent 血缘归因 |
| S1 | 网络行为：连接画像、域名归因 |
| S2+ | 深层安全场景——以集成方式实现 |

**S1 的难点不是采集，是把网络事件归因到人 / Agent**，依赖 S0 建立的 `auid` + `ses` + 血缘能力。这是先做 S0 的理由。
