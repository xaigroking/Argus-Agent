## 总览

| 里程碑 | 目标 | 出口条件 |
|---|---|---|
| **M0** 地基 | 规则下发、auid 打通、**量出真实日志量** | `02-审计规则与验收.md` §4 全部 10 项通过 |

| 1.2 | audit.log 解析器（多行记录合并、十六进制解码、argv 拼装） | 见 1.6 |

| 1.4 | **解析器 fuzz 测试**（Go 原生） | 连续 fuzz 10 分钟无 panic、无 OOM |
| 1.5 | SQLite schema + 写入（见 `01-方案与架构.md` §4） | **`ppid`/`cgroup`/`ses` 必须落库** |
| 1.6 | 解析覆盖率统计 | 语料库中可解析事件 ≥ 99%；不可解析的记入 `unknown` 而非丢弃 |
| 1.7 | 日志轮转跟随、断点续读（记录 offset + inode） | 重启 parse 后不重复、不漏读 |

**安全红线（本阶段起全程适用）：**
- 所有 SQL 参数化，禁止字符串拼接
- 不执行任何来自审计数据的内容
- 解析器以非 root 运行

## M2 · 归因（差异化核心）

> 产出：进程血缘 + Agent 识别 + `argus query`。

| # | 任务 | 完成判据 |
|---|---|---|
| 2.1 | 按事件顺序增量维护 `pid → 祖先` 映射 | 父进程退出后，子进程仍能追到正确祖先 |
| 2.2 | pid 复用处理（`(pid, start_ts)` 主键） | 构造 pid 复用场景，归因不串 |
| 2.3 | cgroup 作为第二锚点 | 两锚点一致时标记可信，不一致标记 `unknown` |
| 2.4 | Agent 识别规则（配置驱动，见 `01` §5.3） | 新增一个 Agent 只需改配置，不改代码 |
| 2.5 | 会话表：登录起止、源 IP、tty | `argus query sessions` 输出正确 |
| 2.6 | `argus query` CLI：按用户 / 会话 / Agent / 时间段 | 四个维度均可查 |
| 2.7 | **端到端验证**：真跑一次 Claude Code 或 Codex，核对归因 | 人工核对该次会话执行的命令，与 Agent 自述对比 |
| 2.8 | 每日静态 HTML 报告 | 无需 Web 服务即可查看 |

**出口：** 2.7 通过 —— 能准确回答"这个 Agent 今天执行了什么、改了哪些文件"，且与 Agent 自述的差异可解释。

**2.7 是整个项目的价值验证点。** 若此处归因不可靠，项目定位不成立，须回到 2.1–2.3 重做。

## S1 · 网络（下一阶段，不在 S0 范围）

| 方向 | 要点 |
|---|---|
| 连接画像 | auditd `connect` 仅给 IP:Port；高频场景事件量极大 |
| 域名归因 | 需旁路 DNS 日志（dnsmasq / unbound / CoreDNS）按时间 + 客户端关联；DoH/DoT 会绕过本机 DNS |
| 深层检测 | **做集成方，不重实现**：消费 Suricata / Falco 告警，补上 auid + 血缘 |

**S1 的难点不是采集，是把网络事件归因到人/Agent** —— 依赖 S0 建立的血缘能力。
